# 上线路线图（2026-11-23）

基于当前实现状态（V2-Lite 全链路验收：e2e teacher-forcing 98.96%、
CUDA graph 11 档、HTTP 全套、覆盖率 79%）给出实测 → 验收 → 上线的实施路径。

## 一、实测（在正确性验证之上补三块）

### 1. 性能实测（当前最大空白）

现状：仅有 kernel 级 microbench（decode 381GB/s 等），**无服务级数字**。

| 指标 | 测法 | 用途 |
|---|---|---|
| TTFT / TPOT | `scripts/load_test.py --stream`，并发扫描 1/4/8/16/32/64 | 延迟 SLA 可达性 |
| 吞吐（tok/s、QPS） | 同上，sustained 30 分钟 | 单卡容量上限 |
| 对标基准 | 同卡同模型跑 vLLM / SGLang | “为什么用 Cascade 而非 vLLM”的决策依据 |
| KV 抖动 / preemption 频率 | 满负荷统计（`/metrics` 的 waiting/running/KV 块） | 398 块（32GB 默认配置）的实际上限 |

### 2. 稳定性实测

- Soak：混合负载（长短 prompt、流式/非流式、随机断连）2–24 小时；
  盯 `/metrics` 的 tokens/requests 单调性与 KV 块回收
- 故障注入：CUDA OOM、引擎步异常（EngineStepError 回执链路已实现）、
  实例重启后 7–8 分钟加载期的流量表现

### 3. 业务适配实测

- 用**真实业务 prompt 分布**重跑 teacher-forcing 对拍（不同领域 tie 级分歧率不同）
- 真实 chat template（多轮 / system / 工具字段）过 tokenizer

## 二、验收（从“对 HF 一致”转向“业务 SLA”）

| Gate | 标准 | 当前状态 |
|---|---|---|
| 数值正确性 | TF ≥98% + 业务分布复测 | ✅ 98.96% + 待业务复测 |

## 三、上线（分阶段）

### 硬约束（部署前必须知道）

- V2-Lite bf16 权重 29.26GB → 单实例 ≥32GB 卡（推荐 48GB）；默认
  163840 上下文在 32GB 卡上 KV 仅 ~398 块、负载紧
- 单卡单实例单 worker；EP 多卡未联调 → 扩吞吐 = 多实例各持权重
- 引擎↔HTTP 为 10ms 轮询桥（asyncio 桥接为后置项）——高 QPS 下放大延迟
- 模型加载 7–8 分钟：K8s readiness `initialDelaySeconds` 必须 ≥480s

### 最小可行部署

```
客户端 → 网关（TLS + 限流 + 鉴权）→ N× Cascade 实例（1 卡 1 模型）
监控：/metrics + DCGM(GPU) → Prometheus → 告警
发布：蓝绿（新实例 8 分钟加载 → probe 绿 → 切流）
```

### 分阶段

- **Phase 0 内部试用（1–2 周）**：内部工具（代码助手/文档问答）先跑，
  真实流量即 soak test
- **Phase 1 灰度（5–10%）**：与基线服务对比错误率/延迟/成本，`/metrics`
  接入监控面板
- **Phase 2 全量**：SLA 达标 + 告警就位 + 故障演练（引擎异常/实例重启）

### 适合现在上的场景

内部工具、低并发、延迟不敏感、单卡容量够。
**暂不适合**：对外高并发、严格延迟 SLA、多卡需求。

## 四、与 vLLM 的定位

Cascade 的竞争力在**可控性与定制纵深**（MTP/批不变/结构化输出的自研路径），
不在生产成熟度。若只需“一个 V2-Lite 服务”，vLLM 更稳；若业务需要深度定制
（特殊调度、投机解码、内嵌引擎），Cascade 价值成立。性能对标数字出来后此
判断将有量化支撑。
